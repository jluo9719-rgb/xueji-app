## 二、必须修复的 Bug 清单（P0）

> 以下问题会导致**功能实际失效或数据错误**，做软件前必须全部修完。

### BUG-01：实体提取 prompt 缺少 f 前缀 —— 长时记忆完全失效 ⭐最严重

- **位置**：`extract_and_entities()` 函数内，约 L456
- **现状**：

  ```python
  prompt = """判断以下用户消息是否包含用户偏好或限制信息...
    用户消息：{query}
    ..."""
  ```

  字符串没有 `f` 前缀，`{query}` 四个字面字符被原样发给模型。模型收到的永远是占位符而不是用户输入。
- **后果**：长时记忆模块从未真正工作过——提取不到任何真实实体。
- **修复**：改为 `prompt = f"""...用户消息：{query}..."""`。
- **验证方法**：输入"我对花生过敏"，检查 SQLite `entity_memory.db` 的 entities 表出现 `过敏=花生` 类记录。

### BUG-02：缓存失效分支漏写向量库 —— 检索结果为空

- **位置**：主流程 else 分支，约 L121–L130
- **现状**：

  ```python
  else:
      print("📦 缓存已失效，正在重建向量库...")
      ...
      vectors = embedder.encode(chunks)   # 只算了向量
      cache_utils.save_vector_version()   # 直接保存版本号
      # ❌ 缺少 collection.add(...)！
  ```

- **后果**：该分支下 ChromaDB 是空库，所有 RAG 检索返回空，且版本号已被标记为最新，**不会自愈**。
- **修复**：把中间分支的 `collection.add(documents=chunks, embeddings=vectors, ids=ids)` 复制到该分支 `save_vector_version()` 之前。
- **验证方法**：删除 `./cache` 后重启，用 ChromaDB `collection.count()` 确认等于 chunk 数。

### BUG-03：最终回答未持久化 —— 重启丢一轮对话

- **位置**：main_loop 内层循环结束处，约 L600–L604
- **现状**：

  ```python
  save_session()                                    # 先保存
  print("最终回答：", ...)
  messages.append({"role":"assistant", ...})        # 后追加 ❌
  ```

- **后果**：AI 的每轮最终回答都不在 Redis 里，程序重启后丢失最后一轮 AI 回复。
- **修复**：把 `messages.append(...)` 移到 `save_session()` 之前。
- **验证方法**：对话两轮 → Ctrl+C 退出 → 重启 → 问"我刚才问了什么"，AI 应能答出。

### BUG-04：新实体清空旧记忆表

- **位置**：`extract_and_entities()` 内，约 L480
- **现状**：`c.execute("DELETE FROM entities")` —— 每次提取到新实体就清空整张表。
- **后果**：用户说"我对花生过敏"后再说"我喜欢川菜"，过敏记忆被抹掉。
- **修复**：删除 DELETE 语句，仅保留 `INSERT OR REPLACE`（key 相同则更新，不同则新增）。
- **进阶建议**：后续加 `updated_at` 字段和过期/手动删除能力（见 5.7）。

### BUG-05：工具描述库重复写入导致启动报错

- **位置**：约 L341–L356
- **现状**：每次启动都执行 `tool_collection.add(...)` 且 ID 固定为 `tool_0/tool_1`，第二次启动 ChromaDB 抛 ID 冲突异常。
- **修复**（三选一，推荐 a）：
  - a. 写入前判断：`if tool_collection.count() == 0: tool_collection.add(...)`；
  - b. 改用 `tool_collection.upsert(...)`；
  - c. 启动时先 `client_chromadb.delete_collection("tool")` 再重建。
- **注意**：若未来支持"动态增删工具"，选方案 c 最干净。

### BUG-06：CrossEncoder 每次检索重新加载 —— 单次卡顿几十秒

- **位置**：`multi_retrive()` L223 与 `rag_retrive()` L249 各 new 一次
- **现状**：`bge-reranker-large` 约 1.3GB，每次调用都从磁盘加载。
- **修复**：移到文件顶部初始化区加载一次，全局引用：

  ```python
  reranker = CrossEncoder("BAAI/bge-reranker-large")   # 全局唯一
  ```
- **收益**：检索延迟从"几十秒级"降到"亚秒级"（首次加载后）。

### BUG-07：async 事件循环被同步 LLM 调用阻塞

- **位置**：`main_loop()` 及其调用的 `query_rewrite` / `summarize_old_messages` 等
- **现状**：函数是 async 的，但 `client.messages.create` 是同步 SDK 调用，会卡住整个事件循环；并行搜索的收益被抵消。
- **修复**：改用 `AsyncAnthropic`，所有 LLM 调用点改为 `await client.messages.create(...)`；或短期方案用 `asyncio.to_thread(client.messages.create, ...)` 包裹。
- **优先级**：P0 末尾（不影响正确性，影响并发性能）。

### BUG-08：API 密钥明文存放 —— 安全隐患 ⭐软件发布前必须解决

- **位置**：`load_dotenv()`（L9）+ 项目根目录 `.env` 文件
- **现状**：`ANTHROPIC_API_KEY`、`ANTHROPIC_BASE_URL`、`SERPER_API_KEY` 以明文存在项目目录的 `.env` 文件里。任何拿到文件夹的人（或误提交到 Git）都能直接读走密钥。
- **后果**：
  - 打包成软件发给用户时，要么泄露自己的密钥，要么要求用户手动改源码；
  - `.env` 一旦进 Git 历史，即使后续删除也仍可被检出。
- **修复方案**：改用 **Windows 凭据管理器（OS 级隐藏存储）**，详见 [8.6 凭证安全管理方案](#86-凭证安全管理方案)。要点：
  1. 新增 `setup_credentials.py` 一次性配置脚本，密钥写入系统凭据管理器；
  2. 运行时通过 `keyring` 库读取，环境变量仅作兜底；
  3. 删除项目内 `.env`，`.gitignore` 永久排除；
  4. 密钥永不打印到日志。

## 五、功能添加路线图

### P0 —— 软件及格线（MVP 必须）

#### 5.1 流式输出（SSE）

- **现状痛点**：用户干等 10~30 秒才看到完整回答。
- **做法**：后端 FastAPI 用 `StreamingResponse(media_type="text/event-stream")`；引擎侧 `stream=True` 逐 token yield；前端 `fetch` + `ReadableStream` 渲染。
- **注意**：thinking 块可作为独立事件类型 `event: thinking` 推送，前端折叠展示。

#### 5.2 多会话管理

- **现状痛点**：Redis 只有单一 `"session"` 键，所有对话混在一起。
- **做法**：
  - 键设计：`session:{session_id}` → messages JSON；另维护 `sessions:index`（列表，含标题/时间）。
  - API：`GET /sessions`（列表）、`POST /sessions`（新建）、`DELETE /sessions/{id}`、`GET /sessions/{id}/messages`。
  - 标题自动生成：首轮提问让 LLM 生成 ≤10 字标题。

#### 5.3 文档上传与管理（激活 pymupdf4llm）

- **现状痛点**：知识库写死一个 txt 手册；`pymupdf4llm` 已安装却未使用。
- **做法**：
  - `POST /documents`：上传 pdf/txt/md → pymupdf4llm 转 Markdown → 走现有粗切+细切管线 → 以 `doc_id` 为前缀写入独立 collection（如 `kb_{doc_id}`）。
  - `GET /documents`：列出知识库文档（名称、chunk 数、状态）。
  - `DELETE /documents/{id}`：下线文档。
  - 检索时跨 collection 或合并查询。
- **意义**：这是产品从"演示 demo"变成"可用软件"的核心功能。

#### 5.4 引用溯源

- **做法**：chunk 入库时 metadata 记录 `{doc_name, section_title, chunk_id}`；重排后的 Top5 连同 metadata 返回；system prompt 要求回答末尾标注来源；前端渲染成可点击展开原文的角标。
- **验收**：问一个手册里的问题，回答下方出现"来源：《内部控制管理手册》§x.x"+ 可展开的原文片段。

#### 5.5 检索过程可视化

- **做法**：引擎各阶段向前端推送状态事件：
  `拆解问题中 → 改写为 N 个查询 → 向量+BM25 检索 → 重排 → 反思审核(第x次) → 生成回答中`
- **实现**：SSE 事件流里穿插 `event: status`；前端做成时间线/步骤条动画。
- **意义**：多 agent 协作是你项目的最大卖点，可视化让它"看得见"。

### P1 —— 体验增强

#### 5.6 Token 用量与成本统计

- 在统一封装的 `llm_call()` 里累加 `response.usage.input_tokens/output_tokens` 到 SQLite 表 `usage(session_id, ts, model, in_tok, out_tok)`。
- 前端侧边栏显示本次会话累计 token；导出日报表。

#### 5.7 记忆管理页

- 列表展示 SQLite 中全部实体记忆；支持编辑/删除/新增。
- 配合 BUG-04 修复后，用户能看到"AI 到底记住了我什么"，建立信任。

#### 5.8 对话导出

- `GET /sessions/{id}/export?format=md` 导出 Markdown；前端一键下载。

#### 5.9 重新生成 / 停止按钮

- 前端"停止"：后端收到 abort 信号取消当前流（asyncio.CancelledError 处理）。
- "重新生成"：回退最后一条 assistant 消息重跑。

### P2 —— 进阶方向

| 功能 | 说明 |
|---|---|

#### 文件一：`setup_credentials.py`（一次性配置脚本）

```python
"""首次使用前运行一次：python setup_credentials.py
   密钥写入 Windows 凭据管理器，之后可删除本脚本产生的明文输入记录。"""
import getpass
import keyring
import sys

SERVICE = "MultiAgentApp"          # 凭据集名称（软件名）
FIELDS = {
    "api_key":  "请输入 ANTHROPIC_API_KEY",
    "base_url": "请输入 ANTHROPIC_BASE_URL（直接回车用官方默认）",
    "serper_key": "请输入 SERPER_API_KEY",
}

def main():
    print(f"=== {SERVICE} 凭证配置（写入 Windows 凭据管理器）===\n")
    for field, tip in FIELDS.items():
        if "KEY" in field.upper():
            value = getpass.getpass(f"{tip}（输入不回显）: ").strip()
        else:
            value = input(f"{tip}: ").strip() or "https://api.anthropic.com"
        if not value:
            print(f"⚠️ 跳过 {field}")
            continue
        keyring.set_password(SERVICE, field, value)
        print(f"✅ {field} 已安全存储")
    print("\n完成！凭据可在 控制面板 → 用户账户 → 凭据管理器 → Windows 凭据 中查看。")

if __name__ == "__main__":
    sys.exit(main())
```

#### 文件二：`core/credentials.py`（运行时读取模块）

```python
"""统一凭证读取：优先 Windows 凭据管理器，环境变量兜底（便于 CI/服务器部署）。"""
import os
import keyring

SERVICE = "MultiAgentApp"

def get_credential(field: str, required: bool = True) -> str | None:
    # 1) 先查系统凭据管理器（OS 级隐藏存储）
    value = keyring.get_password(SERVICE, field)
    # 2) 兜底：环境变量（服务器/CI 场景）
    if not value:
        value = os.getenv(field.upper())
    if required and not value:
        raise RuntimeError(
            f"缺少凭证 [{field}]。请先运行: python setup_credentials.py"
        )
    return value

def get_anthropic_config():
    return (
        get_credential("api_key"),
        get_credential("base_url", required=False) or "https://api.anthropic.com",
    )

def get_serper_key():
    return get_credential("serper_key")
```

### 9.9 产品方向定位（2026-09-01）：学习/备考助手 + 五~八期路线图

**背景**：纯知识库问答赛道拥挤（FastGPT/MaxKB/Dify/Cherry 等），孤立联网搜索无场景支撑（鸡肋）。经讨论确定产品方向为 **方向 A：学习/备考助手**，核心是学习闭环：

> 聊天（暴露薄弱点）→ 错题本（沉淀）→ 出类似题（检测）→ 更新掌握状态 → 循环

**功能蓝图**：
- 知识库上传：支持几百页讲义/真题等大文件，**拖入即后台索引**（不等提问时才建）
- 错题本：会话中 LLM 自动判断"是否暴露知识点困惑"并收录卡片（原问题/正确解答/混淆点/来源会话/掌握状态）；聊天框有手动收录按钮；可导出下载
- 出题：从错题本/章节生成检测试卷（**基于检索原文出题**，带答案+解析+出处——原计划"引用溯源"在此落地）；出题 Agent + 审题 Agent 双协作；试卷可下载
- 多聊天窗口 + 会话时间线

**路线图**（顺序不可颠倒：错题本靠大知识库喂，出题靠错题本供弹药）：

| 期数 | 内容 | 验收效果 |
|---|---|---|
| 第五期 | 知识库上传/管理：POST/GET/DELETE /documents；**异步索引**（状态 processing→ready + 进度实时上报）；按文档增量索引（kb_id/doc_id metadata，传新文件不重嵌旧文件）；内容 hash 去重；空库优雅降级；docx 支持（python-docx） | 拖入几百页讲义，能查能问 |
| 第六期 | 错题本：实体记忆（SQLite 键值）升级为知识点卡片表；自动捕捉+手动收录+管理页+导出 md | 聊一晚，错题本自动多 N 张卡，可下载 |
| 第七期 | 出题：基于检索 chunk 出题（选择/填空/简答+答案键），出题+审题双 Agent，试卷拼装下载 | 一键生成"薄弱点检测卷" |
| 第八期 | UI 整体改版：聊天/错题本/出题三大区域 + 会话时间线 + 主题美化 + 引用角标 | 产品化外观 |

**存储架构确认（无需任何数据库服务器）**：ChromaDB 为嵌入式数据库（同 SQLite 思路），跑在应用进程内，数据即本地文件夹：

| 本地路径（daima/ 下） | 内容 |
|---|---|
| `chroma_db/` | 向量库本体（Chroma 持久化） |
| `cache/` | chunks 缓存、BM25 索引 pkl、版本标记 |
| `entity_memory.db` | 长期记忆（SQLite） |
| `data/uploads/`（第五期新增） | 用户上传的原始文件 |

- Redis 可选不装（内存兜底现状即可用）；唯一外部依赖 = 用户自己的 LLM API；嵌入/重排模型首次下载后本地缓存
- 备份=复制文件夹；用户数据全部留在本机（隐私卖点）
- 独立向量库服务器（Milvus/Qdrant/PGVector）仅在多用户并发/海量向量/分布式时才需要，单机形态用不上

**其他决定**：联网搜索保留，但降级为"工具注册制可插拔"的扩展示例，不作核心功能。先出一版跑通闭环，后续按实际使用反馈优化。

**过程中发现并修复的问题**（新 UI 除两个 TODO 外的 8 处缺陷）：

1. 时间线读 `s.session_id`，后端字段实际是 `id`
2. `POST /sessions` 漏传必填的 `session_id`（后端 422）→ 前端生成 `s_${Date.now()}`
3. 错题本读 `data.mistakes` / `data.total`，后端实际返回 `data.items` / `data.stats`
4. 会话索引没有 `updated_at`，时间线只能按 `created_at` 排序 → 后端补刷新
5. 会话标题用 `innerHTML` 拼接（XSS 风险）→ 改 `createElement` + `textContent`
6. Markdown 完全没渲染（`<pre>` 包原文）→ 补渲染器
7. **`user_turns` 虚高导致标题永不自动改名**：会话消息里混有两种 `role=user` 的非用户发言——工具回传（`content` 是 block 列表）和反思注入的「请结合这个新线索继续检索：」（字符串）。旧统计把它们都算一轮，于是只要用过检索工具 `user_turns` 就 > 1，首轮提问改标题的条件 `user_turns <= 1` 永不成立，时间线一直显示「会话 s_xxx」。修复：`count_user_turns()` 只数「content 是字符串且不是合成提示」的消息
8. 上下文压缩注入的 `system` 总结消息被前端当成聊天气泡渲染 → `loadChatMessages` 跳过 `role === 'system'`

**LLM 通道切换（对应 9.3 已同步更新）**：

- 原中转站 `share.hkai25.top` 对 `deepseek-v4-flash` 返回 503 `model_not_found`（No available channel under group linuxdo），重试后转 429，**该模型已彻底不可用**

- 该通道的两个关键差异，各对应一处代码适配：
  - **把并发限流也报成 429**（无 `retry-after` 头，通常连续 1~3 次 429 后放行）。原实现「429 一律判定欠费不重试」会让每次提问直接失败 → 改为按错误内容区分：含 quota/欠费/余额 才放弃，纯限流退避重试

- 代价：单轮明显变慢，带 4 轮检索的完整问答实测约 8~18 分钟
